# A CORS wildcard matches one label over a host of at least two

An installed Zendesk app is served from `https://<app-id>.apps.zdusercontent.com` — app-id `1231469` on the Forest app, measured 2026-09-15 — so an exact allow-list forces the customer to copy an opaque id they never chose. `BFF_ALLOWED_ORIGINS` and the per-key `allowedOrigins` therefore accept an entry whose leading host label is `*`, matching exactly one DNS label there, with the scheme and the port still compared exactly and never wildcarded. The shape is the whole security argument: one label, leading position only, so `https://1231469.apps.zdusercontent.com` passes while `https://a.b.apps.zdusercontent.com` and the apex `https://apps.zdusercontent.com` do not, and a suffix can never be widened after the fact by adding depth to the request. The host left after `*.` must be at least two non-empty labels. That floor is what refuses `https://*.com`, and it is deliberately a label count rather than a public-suffix check: a PSL is a dependency plus a refresh cadence the BFF would have to keep current or silently drift, and the list it would guard is operator-controlled, not user-supplied. The cost is stated rather than hidden — `https://*.co.uk` and `https://*.github.io` clear the floor and would admit every site under those suffixes, which is why the README and the `allowedOrigins` JSDoc both name it as an operator responsibility. The non-empty requirement on every remaining label is not cosmetic: `https://*.com.` and `https://*..com` survive a plain two-label count, and a browser on `https://evil.com./` sends `Origin: https://evil.com.`, so the trailing dot alone would defeat the floor. What makes the widening acceptable at all is that CORS is not the authentication boundary here: a `bff_access` session or an API key is still required on every call, and another origin cannot read the Forest app's tokens. Two consequences follow from using one matcher for both layers. A request `Origin` carrying a `*` of its own is refused outright, because otherwise `https://app-*.zendesk.com` reads as a single label and matches `https://*.zendesk.com`; and the per-key overlap check that feeds the startup warning compares entries through a dedicated intersection rather than through the request path, so a key whose pattern the parser refuses is reported as unable to pass instead of appearing to overlap. Rejected: a public-suffix list, for the dependency and the drift; multi-label matching, which turns one wildcard into an unbounded subtree; and a wildcard on the scheme or the port, which buys nothing and removes the two comparisons that stay exact.
